# API Integration

## Overview

This frontend is a Next.js 16 App Router application with a clear separation between server-side data fetching, client-side React Query state, and UI components. The backend is integrated through Axios-based service functions, server actions, and TanStack Query hooks.

- Framework: Next.js 16 App Router
- API communication method: Axios via [src/lib/axios.ts](src/lib/axios.ts)
- Axios configuration: `baseURL` comes from `NEXT_PUBLIC_API_URL`, and requests use `withCredentials: true`
- Authentication strategy: HTTP-only access and refresh cookies are set by server actions and server-side services; route protection is enforced in [src/proxy.ts](src/proxy.ts)
- State management: TanStack Query is wired through [src/providers/query-provider.tsx](src/providers/query-provider.tsx) and [src/lib/query-client.ts](src/lib/query-client.ts)
- Server Actions: Used for login and registration in [src/app/(authGroup)/\_action/login.ts](<src/app/(authGroup)/_action/login.ts>) and [src/app/(authGroup)/\_action/register.ts](<src/app/(authGroup)/_action/register.ts>)

The payment flow is implemented as:

1. The user selects rental dates and submits the rental request.
2. The frontend calls the rental creation endpoint.
3. The frontend calls the checkout session endpoint using the rental order ID.
4. The frontend redirects to the returned Stripe checkout URL.
5. The app exposes success and cancel pages for the post-payment experience.

No webhook handler or query-string payment verification flow is implemented in the current frontend codebase.

# Middleware Integration

The route protection layer lives in [src/proxy.ts](src/proxy.ts). It acts as the middleware-equivalent guard for the App Router.

- Protected routes: dashboard, provider dashboard, and admin dashboard areas require an authenticated access token
- JWT authentication: access and refresh tokens are verified using the JWT utilities in [src/utils/jwt.ts](src/utils/jwt.ts)
- Refresh token flow: when the access token is invalid but the refresh token is still valid, the app calls [src/services/refreshToken.ts](src/services/refreshToken.ts) and reissues the session context
- Role-based route protection: admin routes require `ADMIN`, provider routes require `PROVIDER`, and customer dashboard routes require `CUSTOMER`
- Public routes: `/`, `/gears`, `/about`, `/contact`, `/404`, `/403`, `/login`, and `/register`

The auth cookies are set by the server-side login action in [src/app/(authGroup)/\_action/login.ts](<src/app/(authGroup)/_action/login.ts>) and cleared by [src/services/logout.ts](src/services/logout.ts).

# API Error Handling

The application handles API errors in a layered way:

- Server-side services wrap Axios calls in `try/catch` and return a predictable shape such as `{ success: false, message: ... }`
- React Query mutations and query hooks surface errors through toast notifications using Sonner
- Auth forms use `useActionState` and show success or error toasts from the server action result
- The rental checkout flow shows user-facing toasts for validation, login-required access, payment failures, and unexpected errors
- The app has a global error boundary in [src/app/error.tsx](src/app/error.tsx) with [src/components/shared/error/ErrorState.tsx](src/components/shared/error/ErrorState.tsx)
- Loading states are handled by the shared [src/components/shared/loading/Loading.tsx](src/components/shared/loading/Loading.tsx) component and by inline loading conditions in pages such as the dashboard and provider pages
- Validation errors are handled through Zod in [src/app/(dashboardGroup)/provider-dashboard/\_components/GearForm.tsx](<src/app/(dashboardGroup)/provider-dashboard/_components/GearForm.tsx>) and by the auth server action for password mismatches

# Architecture Summary

The frontend follows a layered architecture:

- Separation of concerns: UI components remain focused on rendering, while services own API calls and hooks manage data state
- Service Layer: server-side modules in [src/services](src/services) encapsulate Axios requests and cookie-based auth handling
- Hooks Layer: React Query hooks in [src/hooks](src/hooks) manage caching, invalidation, and mutation flows
- UI Layer: route pages and feature components render data and trigger actions
- Server Components: the public pages, dashboard shell, and many route-level pages use server components to fetch data directly
- Client Components: auth forms, rental checkout, provider/admin dialogs, and query-driven dashboards use client components for interactivity

# Final Notes

- Total endpoints integrated: 13 distinct backend endpoints are consumed by the frontend
- Total React Query hooks: 11 hooks, including 6 queries and 5 mutations
- Authentication flow: login/register via server actions, cookie-based session management, protected route checks, and refresh-token-aware route guarding
- Payment integration: rental creation followed by Stripe checkout session creation and redirect to the returned checkout URL
- Overall integration quality: the app has a consistent service layer and good route-level separation, but it does not currently implement dedicated webhook handling, dedicated refresh-token endpoints, or broader admin/provider statistics endpoints
